# bls-labor-mcp-server — Design

## MCP Surface

### Tools

Four core tools are always registered. DataCanvas (`CANVAS_PROVIDER_TYPE`, default `duckdb`) adds describe and query, and `none` withholds them; `BLS_DATAFRAME_DROP_ENABLED=true` adds drop only when canvas is also enabled.

| Name | Description | Key Inputs | Annotations |
|:-----|:------------|:-----------|:------------|
| `bls_search_series` | Searches BLS series catalog by natural language query, survey, geographic area, or subject keywords to resolve cryptic SeriesIDs. Returns matching series with decoded components (survey, area, item, seasonal flag, and `frequency` for the CU/CW/LN/BD surveys that publish one title at several frequencies) and plain-language names. Use this before `bls_get_series` when you have a concept but not a SeriesID. Under `survey: "OE"` with no OE rows indexed, it composes OEWS SeriesIDs from the OE code tables, each marked `composed: true` and unconfirmed until `bls_get_series` returns it. | `query` (natural language or keyword), `survey` (free-form two-letter LABSTAT code of an indexed survey — CU, CE, LN, LA, JT, SM, …; OE indexed only with `BLS_CATALOG_INCLUDE_OES=true`, otherwise composed), `area` (place name, USPS state code, or FIPS / CBSA / CPI area code; see Search), `seasonal_adjustment` (bool), `limit` (positive integer; clamped to 50), `offset` (paging) | `readOnlyHint: true`, `openWorldHint: false` |
| `bls_get_series` | Fetches time-series data for 1–50 BLS series by SeriesID, with optional year range and BLS-computed period-over-period calculations. Returns observations with metadata and an `available` discriminator for BLS missing-value sentinels; mixed batches preserve valid series. With DataCanvas enabled, results above the inline budget spill and return a `dataset` handle whose rows add nullable `value_numeric` for arithmetic: inspect it with `bls_dataframe_describe`, then query it with `bls_dataframe_query`. Without DataCanvas, all fetched observations return inline. Annual-average rows are opt-in via `annual_average` and independent of the year range. | `series_ids` (nonempty array; canonical first 25 keyless / 50 keyed), `start_year` (int), `end_year` (int), `calculations` (bool), `annual_average` (bool, default false) | `readOnlyHint: true`, `openWorldHint: true`, `idempotentHint: true` |
| `bls_get_latest` | Returns the single most recent observation for one or more BLS series, including `available` when BLS published no value for the newest period. For "what is X right now" questions — use when you need the current value, not history. Internally issues one GET request per series (no batch-latest endpoint exists in the BLS API); prefer `bls_get_series` with a 1-year window when fetching latest values for many series. | `series_ids` (array, 1–10 recommended; up to 50) | `readOnlyHint: true`, `openWorldHint: true`, `idempotentHint: true` |
| `bls_list_surveys` | Lists BLS survey programs with their codes, descriptions, and geographic/subject coverage. Use to discover which survey covers a topic before calling `bls_search_series`. Each row's `searchCoverage` (`indexed` | `composed` | `none`) says whether `bls_search_series` reaches the survey through its offline index, composes its SeriesIDs from code tables (OE), or cannot search it; indexed rows add `seriesIndexed`. Both are absent before the catalog's first load, and the counts are cached at load and after each harvest rather than queried per call. | `category` (enum: prices, employment, wages, productivity, injuries, time_use — optional filter; categories follow the BLS subject areas, and a survey can sit under several) | `readOnlyHint: true`, `openWorldHint: true`, `idempotentHint: true` |
| `bls_dataframe_describe` | List canvas dataframes materialized by `bls_get_series` or `bls_dataframe_query` `register_as`, with provenance, TTL, row count, and column schema. Read-only. Unavailable when `CANVAS_PROVIDER_TYPE=none`. | `name` (optional canvas identifier — omit or leave blank to list all) | `readOnlyHint: true`, `idempotentHint: true`, `openWorldHint: false` |
| `bls_dataframe_query` | Run a single-statement SELECT against canvas dataframes. Supports JOINs, aggregates, window functions, CTEs. Optional `register_as` persists the result as a new dataframe. Read-only: writes, DDL, DROP, COPY, PRAGMA, ATTACH, and external-file table functions are rejected. System catalogs denied at bridge layer. Unavailable when `CANVAS_PROVIDER_TYPE=none`. | `sql` (SELECT statement), `register_as` (optional), `preview` (optional row count), `row_limit` (default 1000, max 10000) | `readOnlyHint: true`, `idempotentHint: true`, `openWorldHint: false` |
| `bls_dataframe_drop` _(opt-in)_ | Drop a canvas dataframe by name. Idempotent. A failed drop keeps the dataframe and raises `canvas_drop_failed`. Requires canvas plus `BLS_DATAFRAME_DROP_ENABLED=true` — off by default since per-table TTL handles cleanup. | `name` (canvas identifier: `df_<id>` or a `register_as` name) | `readOnlyHint: false`, `idempotentHint: true`, `openWorldHint: false`, `destructiveHint: true` |

### `bls_dataframe_describe` / `bls_dataframe_query` / `bls_dataframe_drop`

In-conversation SQL analytics over the dataframes that `bls_get_series` materializes on a shared DuckDB-backed canvas. When `bls_get_series` spills, pass `dataset.name` to `bls_dataframe_describe` to inspect the authoritative snake_case `column_schema`, then use that table name in `bls_dataframe_query` for JOINs, GROUP BY area/industry, and window functions.

The framework-owned `config.canvas.providerType` controls the startup surface. `src/index.ts` defaults `CANVAS_PROVIDER_TYPE` to `duckdb` once `./.env` has loaded and before anything reads it, so a `.env` value of `none` still wins; the MCPB manifest pins `none`. When it is `none`, all three dataframe definitions remain visible in operator metadata through `disabledTool` but are omitted from MCP `tools/list`; server instructions describe complete inline observations instead of a spill workflow. When it is `duckdb`, describe and query are registered, while drop remains independently gated by `BLS_DATAFRAME_DROP_ENABLED`.

- **Read-only by default.** Writes, DDL, DROP, COPY, PRAGMA, ATTACH, and external-file table functions are rejected by the framework SQL gate. System catalogs (`information_schema`, `pg_catalog`, `sqlite_master`, `duckdb_*`) are denied at the bridge layer so callers can't enumerate dataframes they don't already hold a handle for. `bls_dataframe_drop` is the only destructive tool and is opt-in (`BLS_DATAFRAME_DROP_ENABLED=true`); TTL handles cleanup otherwise.
- **Per-table TTL.** Each dataframe has an expiry fixed at creation (default 24 h, override with `BLS_DATASET_TTL_SECONDS`). The canvas itself uses the framework's sliding TTL. Every dataframe operation first sweeps expired entries; an entry whose drop fails keeps its metadata, logs a warning, and is retried by the next operation, which still succeeds.
- **`register_as` chaining.** `bls_dataframe_query` can persist its result as a new dataframe with a fresh TTL — chain analyses without re-running the source query or consuming additional BLS API quota. The stored `column_schema` is the one the canvas reports for the materialized table, read with one extra describe per `register_as` (measured at 1.8–3.3 ms median over 300 runs, against 1.5–2.5 ms for the fastest `register_as` itself; plain queries skip it). A failed read fails the call. The framework's type mapping reports DuckDB types outside its set — `DECIMAL`, `HUGEINT` (`SUM` over an integer column), `SMALLINT`, lists — as `VARCHAR`; the physical column keeps its real type, and SQL over it works.
- **Dataframe names.** `name` on describe and drop follows the canvas identifier rule (`CANVAS_IDENTIFIER_REGEX`: a letter or underscore, then letters, digits, or underscores, at most 63 characters), which every minted `df_<id>` and every accepted `register_as` name satisfies. Drop's required `name` carries the rule in its schema, so a name outside it is rejected at argument validation; drop also rejects a reserved SQL keyword (`select`, `from`, …), which no dataframe can carry. Describe's optional `name` follows the server's blank-means-omitted convention instead: the handler trims it, lists every dataframe when it is blank, and raises `invalid_dataframe_name` with the rule for any other name outside it — a schema pattern would reject the `""` that form-style clients send for an empty field.
- **Drop keeps what it could not drop.** Metadata goes only after the canvas confirms the drop or the table's absence. An acquire or provider failure raises a retryable `canvas_drop_failed` with the provider error as `cause` and leaves the dataframe listed and queryable; a cancelled request fails as cancelled. The shared canvas is replaced only when its stored id reports `canvas_not_found` — any other acquire failure propagates rather than orphaning every table the stored canvas holds.
- **`bls_get_series` output schema.** A successful spill registers every fetched observation and returns `dataset: { name: "df_<id>", row_count: N, expires_at: "…" }`. Inspect `name` with `bls_dataframe_describe`, then use it in `bls_dataframe_query`; when no spill occurs, `dataset` is absent. Registration failure is a typed error rather than a partial success. The spill table's schema is declared, not inferred from the batch: `value_numeric` and every `net_change_*` / `pct_change_*` column are `DOUBLE` (BLS's calculation strings parsed to numbers, a non-numeric one stored as `NULL`), `is_annual_average` and `available` are `BOOLEAN`, the rest `VARCHAR`, all nullable — so a whole-number or all-unavailable batch types the same as any other.

SeriesID inputs are trimmed, uppercased, and deduplicated in first-occurrence order before caps apply. History processes the first 25 without an API key or 50 with one; latest processes the first 50. `unprocessedSeriesIds` returns the exact ordered canonical remainder on both response surfaces. No automatic extra batches are sent. Search clamps `limit` to 50. SQL clamps `row_limit` to 10000 and `preview` to the applied row limit, preserving zero preview; notices disclose requested and applied values. `register_as` still persists the full SQL result.

Live series use local-catalog titles where available and preserve optional BLS `measure` metadata, including a nullable `measure` spill column. Mirror-served series carry `measure` too (structuredContent and a `Measure:` line) for the surveys whose code tables name it — CE, LN, OE, PR, MP, CM, CI, CU, AP, CW, PC, WP, and LA; JT and EC have none, since the API publishes no catalog for them. The catalog-less live re-issue fills `measure` from the index like title, area, and item, and an upstream `measure_data_type` always wins. Omitted year bounds use BLS's three-calendar-year default, subject to coverage. Applied-year enrichment reports effective settings and disclosed upstream reductions rather than echoing an unfulfilled request. Calculation enrichment is true only when every data-bearing series returns actual calculation values; BLS advisories and reductions are preserved on both response surfaces with sensitive values redacted.

## Overview

`bls-labor-mcp-server` wraps the Bureau of Labor Statistics public API (v2), exposing US labor, price, productivity, and employment data. The BLS is the primary source for CPI, unemployment, wages, JOLTS, PPI, occupational employment, and related statistics — predating and often more current than republished FRED series.

The core UX problem is SeriesID resolution: BLS identifiers (`LNS14000000`, `CES0000000001`) encode survey + area + item + seasonal flag in opaque positional codes. `bls_search_series` is the anchor tool — it translates human concepts into SeriesIDs so the other tools can operate.

---

## Requirements

- BLS API v2 endpoint (`https://api.bls.gov/publicAPI/v2/`); optional `BLS_API_KEY` enables registered limits; keyless v2 requests use the unregistered limits
- 500 queries/day per API key; 50 series per request; up to 20 years history per request
- Read-only access — BLS API has no write endpoints
- SeriesID catalog sourced from LABSTAT flat files at `download.bls.gov/pub/time.series/{survey}/` — one `{survey}.series` file + code tables per survey (e.g., `cu.series` = 1.3MB, `ce.series` = 3.9MB, `ln.series` = 15MB; code tables such as `cu.area`, `jt.state`). Only the `{survey}.series` file and its code tables are needed, not the `{survey}.data.*` observation files (those are hundreds of MB). Harvested at startup into an on-disk SQLite index — ~267K series and ~83MB for the 22 default surveys; `bls_search_series` operates entirely offline against this index
- Period-over-period calculations via BLS v2 `calculations: true` boolean; a single flag (you cannot select an individual calculation type), but the API returns whichever the survey supports; a survey supporting neither can return `REQUEST_SUCCEEDED` with its observations and an informational message, no calculation fields; each survey's `allowsNetChange` / `allowsPercentChange` fields (from `GET /surveys/{abbr}`) predict which will come back
- Annual averages via BLS v2 `annualaverage: true` boolean, exposed as `bls_get_series`'s `annual_average` (default false) and independent of the year range. The flag appends a BLS-computed annual-summary row per year, not universally the arithmetic mean — `M13` on monthly-cadence series, `Q05` on quarterly, `S03` on the semiannual cadence CPI also publishes — each named `Annual` beside the real `M01`–`M12` / `Q01`–`Q04` / `S01`–`S02` rows. It is not an additional period, so a caller summing or averaging `observations` double-counts every year unless the rows are excluded; that hazard is why the flag defaults off. `hasAnnualAverages` (from `GET /surveys/{abbr}`) does not predict the rows — LN, CE, LA and SM report `true` yet return none — so `enrichment.annualAverageRows` reports what actually came back. LABSTAT `.data.*` files bake these rows in unconditionally with no flag, so the observations mirror filters them at query time to match the live path
- `api-canvas` / DataCanvas available for tabular spillover when series count × observation count exceeds context budget

**`BlsApiService` resilience:**

| Concern | Decision |
|:--------|:---------|
| Retry boundary | Full fetch + body read + parse pipeline; use `withRetry`. HTTP status is classified before reading the body: retry only 408/429/500/502/503/504 and transport failures. Other HTTP failures stop immediately. |
| Backoff | 1–2s base (rate-limited upstream, 500/day quota makes aggressive retries counterproductive) |
| Operation deadline | One 45-second live-operation budget covers attempts, bodies, backoff, and the single catalog-less reissue. Each attempt receives the remaining budget's abort signal. This retains the four-attempt retry limit and leaves 15 seconds of headroom for a 60-second client deadline; the reissue never restarts the clock. Expiry raises `upstream_timeout`; caller cancellation retains its original reason. |
| 429 handling | Transient HTTP availability failure; an HTTP-200 BLS quota rejection remains `quota_exceeded` and is not retried. |
| Parse failure | Successful HTTP responses containing HTML raise `service_unavailable`; complete malformed JSON raises nonretryable `serialization_failure`. |

**`BlsCatalogService`:** BLS LABSTAT publishes per-survey flat files at `download.bls.gov/pub/time.series/{survey}/`. The relevant files are `{survey}.series` (series-level index: seriesID, code columns, seasonal flag, and usually a `series_title`) and the survey's code tables (e.g., `cu.area`, `cu.item`, `jt.state`). The catalog index needs only `{survey}.series` + the code tables — not the hundreds-of-MB `{survey}.data.*` observation files (those are ingested separately by the optional `BlsObservationsService` mirror, off by default). Series files and code tables are fetched at startup — and again by an hourly check for each survey that has gone stale — and indexed into an on-disk SQLite store (`BLS_CATALOG_DB_PATH`, FTS5-backed) — queried on demand rather than held in memory, so large surveys do not inflate the heap, and the index survives restarts. Search narrows candidates via FTS5 then applies a bespoke relevance rescore. The OES/OEWS wage survey (~6M series / ~1.26 GB; Bun-only, since Node caps a string at 536,870,888 characters) is excluded unless `BLS_CATALOG_INCLUDE_OES=true`; while its rows are not indexed, every check instead stores the small OE code tables (`oe.area` 22 KB / 583 areas, `oe.occupation` 263 KB / 1,104 codes, `oe.datatype` 528 B / 17 types) in `bls_oews_tables` — schedule key `oe-tables`, its own backoff, not gating `complete`, seeded current from a complete state on restart only when a usable set is stored — and search composes OE SeriesIDs from them. Enables full-text + structured search with zero API quota cost. The BLS FAQ explicitly notes there is no API catalog endpoint ("We do not currently have a catalogue of series IDs"), confirming the offline approach is the only path.

- **Code-table joins.** Each `SURVEYS` entry declares which `.series` columns decode to `area`, `item`, `measure`, and (CU, CW, LN, BD) `frequency`, as `{ table, key }` dimensions; only the tables those dimensions name are fetched. A dimension can fall back on a placeholder code: SM's `00000` "Statewide" area falls back to `sm.state`. `ee.datatype` keys on `data_type_code`. A code table is parsed by its header: the code comes from the key column(s), which carry the same names in both files, and the label from the first `_text`/`_name` column. Layouts vary too much for positional parsing — `la.area` opens with `area_type_code`, `ce.industry` puts its label fourth, `pc.product` and `wp.item` key on a column pair (`wp.item` has 377 item codes that are ambiguous without their group), `ec.compensation` keys on `comp_code`, and `ec.group` is space-delimited. An unavailable, unreadable, empty, or structurally invalid declared table fails the survey replacement: keep its complete prior snapshot, including rows otherwise deleted, or omit the survey on a cold index. The `measure` table is the one exception on a cold index: it only labels mirror-served series, so a survey with no indexed rows indexes without a measure rather than not at all. A missing declared key in the series header also fails the survey; an individual unknown row code remains optionally undecoded.
- **Title synthesis.** JT, EC, PR, SM, and EE ship no usable `series_title` (BLS's API catalog title for SM is generic). Their titles join the survey name and an ordered dimension list — JT: data element, industry, state, size class, rate/level (`JOLTS - Quits - Total nonfarm - Total US - All size classes - Rate`); EC: compensation, group, ownership, periodicity; PR: measure, sector, duration; SM: `SAE - State and Area Employment, Hours, and Earnings - {data type} - {industry} - {metro area or state}`; EE: `CES (SIC basis, ended 2003) - {data type} - {industry}`. That is the smallest list giving every row a distinct title + seasonal pair (PR titles are distinct on their own). JT's `area_code` is the constant `00000`, so its `state_code` supplies the area. The JT survey name is the bare acronym: spelled out, "Job Openings and Labor Turnover" would put "job openings" into every JT title.
- **LAUS decodes no `item`.** Its `la.measure` label goes only into the stored `measure` column, which is not full-text indexed. LAUS titles open with their measure ("Unemployment Rate: Texas (S)"); decoding `la.measure` into `item` as well put ~8K state and local rows ahead of the national CPS series for measure queries.
- **Publication frequency.** CU and CW publish each series monthly and semiannually under the same `series_title`, LN publishes monthly/quarterly twins (plus annual-only series), and BD publishes quarterly and annual rows (with area and item, frequency makes all 34,416 of its rows distinct; without it 32,761 are). Their `periodicity_code` decodes through `{abbr}.periodicity` into a `frequency` column (`Monthly`, `Semi-Annual`, `Quarterly`, `Annual`) returned on every result; on the 2026-09-23 files it makes every CU and CW title + seasonal + frequency triple distinct and separates 19,105 of LN's 19,479 same-title rows (the rest differ in other dimensions). Titles stay the upstream `series_title`. The column is not FTS-indexed, and a title suffix was declined: both let a query's `annual` match semiannual rows, putting 8 of them into the top 10 of `cpi annual average`. In the rescore, a query naming `monthly`, `quarterly`, or `semiannual` (`semi-annual`, `semi annual`) as a whole word adds the item-match weight (+1) to rows of that frequency, after the zero-score gate, so the word qualifies a match but never makes one. `annual` is never matched — it names the annual-average period monthly series also carry, and matching it lifts annual-only CPS series over the canonical monthly ones. Frequency is never a tie-break. CI and EC also have a `periodicity_code`, but theirs is a measure type (index, percent change) already in the title.
- **Compensation surveys.** CM (ECEC) and CI (ECI) are the current compensation-cost surveys; EC is the SIC-basis ECI that ended in 2005 and stays indexed under that name. Both ship `series_title`; `area` decodes through `{abbr}.area` (`99999` is `United States (National)`) and `item` through `{abbr}.estimate` (Total compensation, Wages and salaries, a benefit), without which `wages`, `benefits`, and `eci wages and salaries…` still ranked EC or LN rows first. They sit last among the mirrored surveys in `SURVEYS`; that order (`SURVEY_ABBRS`) is the observations ingester's resume cursor.
- **Concept aliases.** `CONCEPT_ALIASES` maps vocabulary the titles never use to surveys whose candidates get +6 in the rescore: `inflation`/`cpi`/`consumer price index` → CU, `ppi`/`producer price index` → WP/PC, `jolts`/`job vacanc` → JT, `compensation`/`employer cost`/`ecec` → CM/CI, `employment cost index`/`eci` → CI, and so on. A phrase matches where a word starts and may run on into the word, so `ppi` never fires inside "shopping" or "happiness" while `job vacanc` still matches "job vacancies" and `payroll` "payrolls". That word-start rule is what makes a bare `eci` safe: as a substring it hit "special", "decision", and "precision". A fired alias phrase's words count as matched on every row of its survey, so `consumer price index all items` needs no `consumer`/`price`/`index` in a title. The boost never widens the candidate pool: besides reordering FTS matches, it can lift only the always-unioned `COMMON_SERIES` headlines past the zero-score gate (`inflation` returns the two CPI-U all-items series), with one exception: a whole-word `core` beside a CPI alias unions CU `All items less food and energy` (117 rows), and beside a PPI alias WP `Final demand less foods and energy` and `Final demand less foods, energy, and trade services` (4 rows). Those core rows join the candidates within the survey filter, count `core` as matched, and take the +8 headline boost; a bare `core` is unchanged. CM and CI hold no headline, so a query of an alias alone (`eci`, `ecec`) still returns only rows whose text matches it — for `eci`, the EC rows whose synthesized titles carry the acronym.
- **Coverage.** `begin_year`, `end_year`, and `end_period` become independently optional `startYear`, `endYear`, and `endPeriod` fields on both search response surfaces. Years must be positive four-digit integers; missing, blank, or malformed values are omitted independently. Normal rows are header-keyed; the recognized EC historical layout and EE, with an unlabeled footnote before their trailing coverage fields, receive that one-field adjustment (`footnoteUnlabeled`). Coverage describes the harvested snapshot and does not establish continuity or discontinuation. The three columns are plain, outside FTS. Ranking reads them only as a tie-break (see Ranking ties): a series is current when its `endYear` is at least its survey's newest `end_year` minus one (unknown coverage counts as current), with the newest years recomputed at load and after each harvest. It hides nothing and adds no output field or label.
- **Index version.** `createCatalogStore` stamps a catalog index version. A bump's migration clears the sync state's completion marker, so an index persisted by an earlier release re-harvests on its first boot after upgrade while it keeps serving; `writeState` cannot clear the marker (it COALESCEs `completed_at`). The current version is 5 (adds the `measure` column and the OE code-table store); version 4's migration adds every missing `frequency`, `start_year`, `end_year`, and `end_period` column: migrations run after the declarative `CREATE TABLE IF NOT EXISTS`, which never alters an existing table, so it checks `PRAGMA table_info` first — a brand-new database already has the columns. Bump the version whenever the harvest's output changes. A change to the configured survey set needs no bump: the survey list below marks the index stale on its own.
- **Freshness.** Freshness is per survey. Each survey's last success is kept in memory, seeded from the sync state's `completedAt` only for a complete harvest of the configured survey list. The index is fresh when every configured survey's last success is within `BLS_CATALOG_CACHE_TTL_HOURS` and it harvested the survey list this deployment configures. Every completed harvest persists that list (the harvested abbreviations in `SURVEYS` order) in the sync state's `checkpoint`; `load()` treats a missing or different list as stale. `complete` is written only once every configured survey has succeeded, with `completedAt` the oldest success. A partial pass records `error` without advancing `completedAt`, and failed surveys keep their prior rows.
- **Refresh.** `setup()` runs the boot `load()` in the background and registers `bls-catalog-refresh`, an hourly (`0 * * * *`) `schedulerService` job on both transports whose tick calls `load()` as one check. An index with no series harvests every survey, up to 3 attempts. Otherwise only due surveys harvest, one attempt each: those whose TTL lapsed, or whose failure backoff ran out (the next check, then 2, 4, 8… checks, capped at `BLS_CATALOG_CACHE_TTL_HOURS` checks). Retry state lives in memory, so a restart over an incomplete index harvests everything. A check with nothing due does no I/O beyond the first check per process reading the sync state. Each failed `.series` logs its file, cause, and next retry. `load()` shares one in-flight run among its callers, so a tick during the boot harvest joins it, and the scheduler skips a tick while the previous tick runs. Searches keep reading the index throughout, and `totalSeries` / `indexedSurveys` update when the harvest completes.
- **Stale rows.** After a survey's upserts, its indexed rows absent from the new `.series` file are deleted; a retry of some surveys deletes only within the surveys it harvested. After the last survey, so are the rows of surveys no longer configured (OES once its opt-in turns off), still compared against the full configured list. A survey yielding no rows — its `.series` request failed, returned non-200, had no `series_id` header column (an HTML error page served with a 200), or ended mid-line — keeps its rows, and a harvest that applies no rows deletes nothing. The mid-line check exists because a close-delimited response cut short resolves on Node and Bun with the partial body (a short `Content-Length` or chunked body rejects instead); every LABSTAT file ends in a line break, and parsing the partial body would delete the missing tail and index a fragment of its last line. A body cut exactly at a line break passes the check. Deletes walk the survey's rows in rowid order off the `survey_abbr` index, 5,000 per transaction like the upserts, and the harvest yields an event-loop turn after every chunk, so a search waits at most one chunk. Deleting 1M synthetic OE rows from a copy of the full index took ~30 s in 200 chunks (median 85 ms, one outlier at 1.1 s); a single `DELETE` of the same rows blocks the loop for ~6 s.
- **Shutdown.** `shutdownBlsCatalogService()` removes the refresh job, then `shutdown()` aborts any in-flight harvest — the fetches, the retry backoff, and a check before every write observe the signal — waits for it to settle, and closes the store. The abort is needed because the store reopens on its next call after `close()`: a harvest left running would keep writing to a reopened handle. The stopped `load()` rejects with the shutdown reason, so an interrupted harvest is never recorded as complete.
- **Search.** One FTS5 candidate query uses the first 32 distinct tokens, expands at most two single-character prefixes, and returns at most 1,000 rows ordered by geographic preference, then bm25. Whole-term tokens keep that mode in the rescore, including SeriesIDs and headline descriptions; longer stems retain prefix matching and ID-fragment matching. Rows matching every required word are admitted first, named-place rows first among them, then bm25 fills the rest; rows with no decoded area are not pushed to the end. The candidates are unioned with an exact-SeriesID lookup, `COMMON_SERIES`, and (when a whole-word `core` accompanies a CPI or PPI alias) that survey's core rows, then rescored in memory. Survey, seasonal, and area filters run in SQL before the cap, so `totalCount` and `capped` describe the filtered pool. The `area` grammar:
  - A USPS code or 2-digit FIPS selects the state: its statewide series, the areas in it (metros reaching into it included), and area-less rows whose title names it as a comma-separated part.
  - Other all-digit codes select by length: 3 a CSA, 4 a CPI area (`0000` is the U.S. city average), 5 a county FIPS or CBSA/MD/LMA code, 7 a state + place FIPS. A code naming no indexed area returns no series. These resolve by SeriesID position (LA CA 8–10; CU/CW 5–8; AP 4–7; LA CN 6–10; LA MT, MC, DV, IM, ID, SA 8–12; LA CT, CS, PT 6–12), precomputed at load in `area-filter.ts`, and expand to every area name sharing a normalized key (lowercase words minus a trailing metropolitan/micropolitan/combined statistical area, census division/region, division, region, csa, msa; `metropolitan division` is kept). The SQL is `area_name IN (SELECT value FROM json_each(?))`, plus the state title rule on area-less rows, and the rescore gate mirrors it.
  - Any other all-digit length matches as a substring and adds a notice naming the valid lengths.
  - Other text is a case-insensitive substring of `area_name`, `title`, or `series_id`, bound as an escaped `LIKE` pattern (`%`, `_`, `\` match literally) through `store.raw()`.

  The area index is rebuilt at load and after each harvest. The same area gate runs over unioned headline and core rows, which qualify only when they match a query word: the +5 an explicit `area` adds applies after the zero-score gate. An exact SeriesID scores before the gate and survives any area. Prefix scores count where a word starts in title, area, item, and headline description, through `startsWord`; SeriesID fragments can match mid-ID. A headline earns its +8 only when its survey's alias fires or it matches more than half the distinct scored tokens, its headline description included. SQLite executes synchronously: these are bounds on terms, expansion, and candidates, rather than a latency guarantee. The unbounded `query` tokenizer, full-query, alias, and frequency checks read caller text in linear time. An `area` longer than 1,000 characters skips the FTS query and matches no row except an exact SeriesID.
- **Geographic relevance.** Without an explicit `area`, the query names an area when it holds every distinctive word of one part of the area name (parts split on `-`, `,`, `/`, `(`, `)`; distinctive = three or more characters, not boilerplate or a function word). That area's rows rank first among the rows matching every query word, and the preference applies only to such rows. National areas never count, nor do parts made only of CPS demographic labels (`white`, `black`, `african`, `american`, `asian`, `hispanic`, `latino`, `men`, `women`); geographic boilerplate (`GEOGRAPHIC_STOP_WORDS`, e.g. `balance`, `part`, `village`, `msa`, `csa`, `cdp`) and standalone modifiers such as `new` or `north` create no preference, and `New York` still matches through `York`. The query's distinctive words are looked up in an in-memory index rebuilt at load and after each harvest, so requests examine only the bounded query terms rather than scanning the catalog's geographic vocabulary. An explicit `area` turns the preference off and keeps its own filtering and ranking.
- **Ranking ties.** Rows order by: exact SeriesID; rows matching every required word (function words `a an and at by for in less of on or per the to with` are not required, and a fired alias phrase's words count as matched on every row of its survey, so the headline boost never lifts a row above one that matches every word); rows in an area the query names; score; then, at equal score, current series (see Coverage); national rows unless `area` is explicit (no decoded area, or `U.S. city average` / `Total US` / the CM/CI `United States (National)` / the opt-in OEWS `National` / `U.S. Total` (LE, LU, IP) / `U.S. totals` (BD) / `All States` (SM)); the JOLTS aggregate (`Total nonfarm`, `All size classes`) ahead of its breakdowns; and finally candidate order. Candidate order is exact, core rows (SeriesID order), headlines, then FTS (all-word rows first, then bm25).
- **Paging.** `offset` slices the rescored list, never the SQL query: paging the bm25 pool would return rows in bm25 order rather than relevance order. Pages reach as deep as the candidate pool (1,000 FTS rows plus the unioned rows); order is deterministic for an unchanged index, because every page runs the identical candidate query and equal-score rows keep its order, and a re-harvest between page calls can reorder it.
- **Indexed surveys.** The set of surveys a `survey` filter can match is read from the index (distinct `survey_abbr`) with the row total, once per load and after each harvest. It is not derived from `SURVEYS`: a survey whose download failed is absent (or keeps the rows of an earlier harvest). A filter on any other code gets a notice listing the indexed codes. The same cached counts back `bls_list_surveys`'s `searchCoverage` and `seriesIndexed`, so no call queries the index.
- **OEWS composition.** Under `survey: "OE"` while no OE rows are indexed, search composes SeriesIDs from the stored OE code tables instead of querying the index: each result is marked `composed: true`, carries no coverage years, and `format()` ends its row `· composed (unconfirmed)`; an exact OE SeriesID decodes even without the survey filter. Composition stops at 50 rows (`capped`). Titles read `{Datatype} for {Occupation} in All Industries in {area | the United States}`. Only existing cells are composed: industry `000000` only; seasonal `U`; detailed occupations and major groups in every area, minor and broad groups national only; no national `16`/`17`; with no data type named, `01`/`03`/`04`. Rows order by occupation, then area (the named area, its state, national), then data type; `average` reads as mean and `salary` as annual. `area` under OE is a USPS state code or 2-digit state FIPS (the state), a 5-digit CBSA, or a 7-digit OEWS area code (`0042660`, `5300000`), and otherwise a substring of an OEWS area name; each named metro or state also composes its state and national rows, which bypass the area gate. Composition keeps its own area matcher beside the general one, since 7-digit OEWS codes never collide with state + place codes.

**`bls_list_surveys` backed by API:** `GET /surveys` returns all survey abbreviations and names; `GET /surveys/{abbr}` returns `allowsNetChange`, `allowsPercentChange`, `hasAnnualAverages`. This is a low-frequency call and can be cached aggressively (30-day process-local TTL); it does not count toward the 500/day quota concern.

## Workflow Analysis

**Common agent chain — natural language → current value:**

| # | Tool | Purpose |
|:--|:-----|:--------|
| 1 | `bls_list_surveys` | Orient to which survey covers the topic (optional; skip if domain is clear) |
| 2 | `bls_search_series` | Resolve concept → SeriesID(s) |
| 3 | `bls_get_latest` | Get current value for resolved SeriesID(s) |

**Common agent chain — trend analysis:**

| # | Tool | Purpose |
|:--|:-----|:--------|
| 1 | `bls_search_series` | Resolve concept → SeriesID(s) |
| 2 | `bls_get_series` | Fetch history with `calculations: true` for YoY/MoM |

`bls_get_series` is the quota-heavy tool (one API call per batch, counts as one query). `bls_get_latest` issues N individual GET requests (one per seriesID) — each counts as one query. For "current value" across many series, `bls_get_series` with a 1-year window is more quota-efficient (one query regardless of series count); `bls_get_latest` is preferable only for a single series where the absolute most recent period matters.

**Common agent chain — multi-series SQL analytics (dataframe path):**

| # | Tool | Purpose |
|:--|:-----|:--------|
| 1 | `bls_search_series` | Resolve concepts → SeriesIDs across surveys or areas |
| 2 | `bls_get_series` | Batch-fetch 1–50 series; result spills to canvas → `dataset: df_<id>` when large |
| 3 | `bls_dataframe_describe` | Inspect the authoritative column schema before writing SQL |
| 4 | `bls_dataframe_query` | JOIN multiple `df_<id>` tables, GROUP BY area/industry, apply window functions (rolling avg, YoY) — canvas SQL counts zero against BLS quota |
| 5 | `bls_dataframe_query` + `register_as` | Persist an intermediate result as a new dataframe to chain further analysis without re-running source SQL |

Canvas SQL is quota-free — only the upstream `bls_get_series` call counts against the 500/day limit. This makes canvas the right path for cross-series JOINs and rolling-window computations, especially when BLS's `calculations: true` flag is insufficient (e.g., trailing-12-month average, area-level variance).

### Output and format() Completeness

Both `bls_get_series` and `bls_get_latest` return structured data that must appear in full in both `structuredContent` (Claude Code) and the `format()` markdown twin (Claude Desktop). The `format()` implementation must render all observation values, not just a count or summary. `bls_search_series` similarly must render decoded series components (survey, area, item, seasonal flag, plain-language name) in `format()` — not just a count of matches.

A series that returns no data must be reported on both surfaces too. `bls_get_series` keeps the SeriesID in `series[]` with `observationCount: 0` and names every empty SeriesID with its reason — an invalid ID, the period coverage, or a failed live fallback — in `enrichment.notice`. In mixed batches, per-series advisories never discard observations returned for other IDs. `format()`'s per-series "no observations" line alone is not sufficient: it never reaches `structuredContent` consumers, and it defers to the notice rather than suggesting a recovery of its own, since only the notice knows which reason applies.

When no requested series returns data at all there is nothing to keep, so the batch raises instead — and the reason follows the composition of the advisories rather than the first invalid ID in the list. All-invalid raises `series_not_found`, all-uncovered raises `no_data_for_period`, and a mixed batch keeps the stricter `series_not_found` because an invalid SeriesID is wrong at any window. The message carries one line per failing SeriesID with every advisory BLS issued about it — a series uncovered across several years draws one per year, and all of them are kept — and a mixed batch overrides the contract's recovery hint with one naming both moves, so the caller is not sent to re-resolve an ID that is already correct.

The mirror path answers identically. `fetchSeries` reconciles the mirror read and any live fallback against the requested SeriesIDs, so service entries preserve input positions; tool inputs are first trimmed, uppercased, deduplicated in first-occurrence order, and capped and an ID neither source resolved is present with zero observations rather than omitted. That entry carries no `failure`: the field reports a BLS advisory about a series, and a miss in the local store is not one — its absence is what selects the generic recovery notice. A live fallback that fails is caught when the mirror served at least one requested series with observations: the missed IDs become zero-observation entries carrying the failure in their own `liveFailure` field (`reason` when typed, `message`, and the calling tool's recovery hint), `enrichment.notice` names them with that reason and recovery rather than sending the caller to `bls_search_series`, and a `warning` log records the missed IDs and reason. When the mirror served nothing, or the request was cancelled, the live error propagates unchanged. Coverage is judged before the annual-average filter, so a series the filter empties keeps its position without spending a live query.

Mirror rows carry no BLS calculations, and `calculations: true` does not route a mirrored series to the live API. Each mirror-served series is marked `source: 'mirror'` inside the service; `bls_get_series` then reports `calculationsApplied: false` when any returned series was mirror-served and names those series in `enrichment.notice`. Live-fallback series in the same result carry BLS calculations as usual.

BLS missing-value rows preserve the raw `value: "-"` for round-tripping and expose `available: false`. Counts distinguish total period rows from available observations; formatted output says unavailable explicitly. DataCanvas rows add nullable `DOUBLE` `value_numeric`, so SQL can aggregate without casting the sentinel. The mirror stores the sentinel row verbatim — `value` is a `TEXT` column that round-trips `-` untouched — and serves it through the same normalization, so both paths report the period as unavailable instead of dropping it. Only a row whose value cell is empty is skipped: that is a malformed row, not a published sentinel.

Mirror rows match the live observation shape. `periodName` comes from a static map in `src/services/bls-periods/period-codes.ts`: `M01`–`M12` → January…December, `Q01`–`Q04` → 1st…4th Quarter, `S01`/`S02` → 1st/2nd Half, `M13`/`Q05`/`S03`/`A01` → Annual; other codes get none. (The `.period` tables are missing for LN, OE, CM, and CI and disagree with the live labels, which is why the map is static.) Footnote codes split on commas in order and render as `code: text` from the survey's stored footnote table; an unknown code stays bare, an empty cell yields no key, and a survey with no table keeps bare codes. The `format()` Period column and the DataCanvas `period_name` filter are filled for mirror rows, and a mirror-served `bls_get_latest` carries both.

## Known Limitations

- **500 queries/day per API key.** `bls_get_series` (POST, up to 50 series) consumes one query regardless of series count. `bls_get_latest` issues one GET per seriesID — fetching 10 series' latest values costs 10 queries. At scale this is the binding constraint; prefer `bls_get_series` with a narrow year window for multi-series latest-value needs. Response metadata surfaces an estimated remaining quota when the API returns it. Multi-tenant hosted deployments need per-tenant key support or a quota-sharing strategy outside this server's scope.
- **20-year history window, and both bounds or neither.** BLS v2 caps history at 20 years per request, so longer time series require multiple calls. It also requires `startyear` and `endyear` together and rejects either one alone, spending a daily query to say so. `bls_get_series` resolves the pair in the handler before any request: `start_year` alone takes the current year as `end_year`, capped at `start_year + 19` with `enrichment.notice` naming the cap when the window rather than the current year decided it; `end_year` alone is rejected pre-request as `no_data_for_period` naming the missing bound, since BLS applies no default start year alongside an explicit end year. Resolving once, in the handler, is what keeps the observations mirror and the live API on the same window. `enrichment.startYearApplied` / `endYearApplied` report what was applied, not what was asked for.
- **SeriesID catalog freshness.** The catalog index reflects the LABSTAT flat files at its last harvest, which runs at startup when the index is empty, a survey is older than `BLS_CATALOG_CACHE_TTL_HOURS` (default 7 days), or the index harvested a different survey set, and within an hour of a survey's TTL lapsing while the server runs; a failed survey retries after a growing number of hourly checks. New series or geographic area changes won't appear until the next harvest; retired series leave the index then. `bls_search_series` may miss very recently added series.
- **A large survey parses in one synchronous pass.** Deletes and upserts yield between 5,000-row chunks, but each survey's `.series` text is split and parsed in one go. For the default surveys that is short — the longest stall in a cold harvest of the 2026-09-23 files measured 186 ms; with `BLS_CATALOG_INCLUDE_OES=true`, OES (~6M rows, ~1.26 GB) holds the event loop for its whole parse.
- **No geographic geocoding.** Beyond the code grammar (see Search), the `area` filter is a case-insensitive substring match on the decoded area name, the title, and the SeriesID — a lookup, not a geocoder. Unusual MSA names or abbreviations may not match. A two-letter USPS code always means the state: `LA`, `MT`, `CT`, `MD`, `CA`, `IN`, `OR`, `ID`, `DE`, `PA`, … always name the state and never match a SeriesID fragment, so use a longer fragment (`MT53`) or `survey`. A code reaches other surveys only through a shared normalized area name; LAUS BS/RD codes and CI/CM area codes are reached by name or substring only. LAUS county names identical to their MSA's base name (`Macon-Bibb County, GA`, `Carson City, NV`) share a key, so county 13021 also returns Macon MSA rows and CBSA 31420 the county's rows.
- **Composed OEWS SeriesIDs are unconfirmed.** Search composes OE IDs from code tables, which cannot know which occupation–area cells BLS publishes. For an OEWS ID BLS reports nonexistent, `bls_get_series` and `bls_get_latest` name the state or national row in the per-ID text ("BLS leaves many OEWS occupation–area cells unpublished; request [the state row OEUS… or ]the national row OEUN… for the same occupation and data type."); the static `series_not_found` recovery is unchanged.
- **Calculations are BLS-server-side, requested via a single flag.** `calculations: true` requests both net change and percent change — individual types cannot be selected — but the API returns whichever the survey supports (CPI/PPI return percent change only). An advisory that a series does not produce calculations preserves its observations; an explicit “does not support calculations” rejection raises `calculations_not_supported`. A survey supporting neither can return `REQUEST_SUCCEEDED` with its observations, adding an informational `message[]` entry ("BLS does not produce calculations for Series …") and no calculation fields. The `allowsNetChange`/`allowsPercentChange` flags are therefore predictive only — `bls_get_series` passes the flag through unconditionally and never gates on them. A series served from the observations mirror carries no calculations at all; `calculationsApplied` is then `false` and the notice names it. The flag is true only when every data-bearing series contains actual calculation values, not merely because calculations were requested.
- **BLS's generic rejection is catalog-correlated, and costs one extra query.** Both live calls request catalog metadata (`catalog: true` on the batch POST, `catalog=true` on the latest GET). With it on, BLS intermittently answers a request holding a nonexistent SeriesID — malformed or well-formed — with `REQUEST_FAILED`, the message "Your request has failed. Please check your input parameters, and try your request again.", and `Results: null`, naming no series: 16 of 27 sequential live probes on 2026-09-24, against 0 of 14 for requests holding only valid IDs and 0 of 25 for the same invalid-ID requests without catalog metadata. The service re-issues such a request once without catalog metadata — one extra query, spent only on that answer — then parses the per-series advisories as usual and fills title/area/item/seasonality from the local catalog index where it covers the series; a series outside the index comes back without those fields. A second generic answer stays `request_rejected`.
- **Survey capability flags are a baked-in table, not a live read.** Only `GET /surveys/{abbr}` carries `allowsNetChange`/`allowsPercentChange`/`hasAnnualAverages`; the bulk `GET /surveys` omits them. Reading them live would cost ~70 queries whenever the process-local survey cache lapsed, so `SURVEY_CAPABILITIES` in `bls-api-service.ts` holds a swept snapshot of all 70 abbreviations, merged at list time. It needs a re-sweep only when BLS adds or changes a survey.
- **Dataframe tools require the DuckDB canvas (`CANVAS_PROVIDER_TYPE=duckdb`, the default).** DuckDB has no V8-isolate build; it fails closed on Cloudflare Workers with a `ConfigurationError` at init time. Node.js only. When canvas is disabled (`none`), the dataframe definitions remain operator-visible but are omitted from MCP `tools/list`; `bls_get_series` returns the complete result inline, regardless of its size.

## Decisions Log

### Answered questions

- **Curated lookup table vs. search-only for SeriesID resolution** → offline catalog search from BLS flat files, with a curated "common series" shortlist embedded in the index for high-frequency queries (unemployment rate, CPI-U, nonfarm payrolls). The flat files cover everything; the shortlist just improves ranking for known-common asks. No separate lookup table tool needed.
- **Calculations: BLS flag vs. local computation** → BLS v2 `calculations` flag. One fewer moving part, always consistent with BLS's published numbers. Local computation adds complexity with no fidelity gain for the use cases here.
- **Area-code resolution: separate tool vs. fold into `bls_search_series`** → fold into `bls_search_series` as an `area` parameter. It's a filter, not a workflow step — a dedicated area-lookup tool would just be a pre-step agents forget to use. The search tool accepts state name, MSA, or FIPS and resolves internally.
- **Area-code resolution: how codes map to areas** → by SeriesID position, precomputed at load so search pays nothing; names expand by normalized key rather than per-survey code maps, so merged surveys need no code. The `metropolitan division` suffix is kept, because stripping it merged Atlanta MD with its MSA and Lake County IL MD with the county. The state title rule is limited to area-less rows (lossless on the default catalog, and cheaper). Unknown all-digit lengths get substring matching plus a notice rather than rejection.
- **Catalog retry state: persisted vs. in memory** → in memory. Persisting it needs a schema change, and a restart already re-harvests an incomplete index. Backoff counts hourly checks, not hours: the cron fires at the top of the hour, so a wall-clock 1 h backoff would land just short of the next tick and become 2 h.
- **Mirror footnotes and period names** → footnote text is decoded at read time from a stored copy of each survey's table, with no row backfill, so rewording propagates at the next sync. The footnote fetch is its own pass so a failed table cannot hold the checkpoint. Period names come from a static map because the `.period` tables are missing for LN, OE, CM, and CI and disagree with the live labels. The v3 store migration clears the resume cursor as well as the checkpoint.
- **Mirror file discovery** → the directory listing `{base}/{abbr}/`, not `{abbr}.txt`: every linked `{abbr}.data.*` file is read under its served name, which is how PC joined the mirror.
- **`bls_get_latest` vs. collapsing into `bls_get_series`** → kept as a separate tool. The "current value" ask is extremely common, the call is cheaper in user-cognitive overhead, and the description signals clearly when to use it vs. history. A `mode` consolidation would obscure the choice.
- **DataCanvas on by default** → `src/index.ts` defaults the framework's `CANVAS_PROVIDER_TYPE` (framework default `none`) to `duckdb`, to enable SQL analysis of large `bls_get_series` results; `none` disables it. The MCPB manifest pins `none` because the bundle strips DuckDB's native binding, and a bundle running the canvas would fail on its first staging call. Activated in `bls_get_series` when series × observation count would overflow context. `bls_get_latest` never spills — result set is always bounded.
- **v1 vs. v2 API** → v2 only. v1 requires no key but has severe throttling (10 series/request, no calculations flag). A key enables registered v2 limits; keyless use retains v2 with unregistered limits.
- **Prompts** → none. BLS queries are factual lookups; there's no recurring LLM-interaction pattern that benefits from a template.

- **Why expose dataframe tools at all?** `bls_get_series` can return up to 50 series × 20 years × 12 months = 12,000 observations in a single call. That's comfortably within context for a few series but blows it for broad multi-survey fetches. More importantly, the interesting economic analysis (seasonal decomposition, cross-survey JOIN, geographic variance, rolling averages) requires arbitrary SQL — something `bls_get_series` can never provide inline. Canvas SQL is quota-free; only the upstream fetch counts against the 500/day limit.
- **Why opt-in drop?** Per-table TTL (default 24 h) handles lifecycle for normal use. Making drop always-on would give agents a destructive tool they don't need in the common case; opt-in preserves the read-only posture for deployments that don't need early cleanup.
- **Why expose `register_as` chaining in `bls_dataframe_query`?** Without it, every derived analysis (e.g., "compute 12-month rolling avg, then JOIN that with JOLTS data") requires re-running the full source SQL each time. `register_as` lets the agent materialize an intermediate step as a named dataframe with a fresh TTL, enabling multi-hop analyses within a session.
- **How does this interact with BLS's 500/day quota?** Canvas SQL operations (`bls_dataframe_describe`, `bls_dataframe_query`, `bls_dataframe_drop`) make no BLS API calls — zero quota consumed. The quota gate is at `bls_get_series` and `bls_get_latest`. Once data is on canvas, agents can run unlimited SQL against it without touching quota.

### Options declined

- **`bls_decode_series_id` tool** → declined. Decoding is better done as enriched output in `bls_search_series` results (return the decoded components alongside the ID). A standalone decode tool adds a round-trip for no workflow benefit.
- **`bls_compare_series` tool** → declined. Cross-series comparison is arithmetic the agent can do from `bls_get_series` output. A dedicated comparison tool would be pure wrapper around data the agent already has.
- **App tool for tabular results** → declined. No MCP Apps-capable client justification; DataCanvas via `api-canvas` handles the spillover case without the iframe/CSP/format-twin maintenance cost.
- **Time-series resources** → declined. BLS observations change over time and remain tool results; the stable guide resource provides usage instructions rather than observations.
- **Catalog refresh by `setTimeout(ttl)`** → declined for an hourly scheduler check. Timers clamp delays above 2^31−1 ms (~596 h), and `BLS_CATALOG_CACHE_TTL_HOURS` has no upper bound, so a long TTL would fire at once and loop.
- **Catalog config staleness through `CATALOG_INDEX_VERSION`** → declined for the persisted survey list. Index-version migrations run only when the code constant rises and cannot see the runtime environment, so an OES off → on → off toggle has no monotonic version. Freshness follows the refresh status and configured survey list rather than `indexedSurveys`: retained rows do not prove that a survey refreshed successfully.
- **Catalog stale-row removal by generation column** (`DELETE WHERE gen != current`) → declined for a per-survey diff, which needs no schema migration.
- **Routing `calculations: true` past the observations mirror to the live API** → declined for serving the mirror's rows and reporting `calculationsApplied: false` with a notice. Routing would spend a daily query on every such request the mirror answers today, and would fail outright once the quota is gone — the case where the mirror is the only source still answering.
- **Recovering BLS's generic rejection by SeriesID shape check, per-ID split, or bisection** → declined for one catalog-free re-issue. Well-formed IDs (`LNS99999999`) and alphanumeric ones (`BOGUS123`) draw the rejection too, 510 valid PC SeriesIDs contain `-`, and a split or bisected leg still sends catalog metadata, so a lone invalid ID drew the rejection in 2 of 3 POSTs and 3 of 4 latest GETs. Dropping catalog metadata from every request was declined too: it would cost title/area/item/seasonality for every survey outside the offline index.
- **`register_as` column types from the returned rows, or a `VARCHAR` fallback when the schema read fails** → declined for the canvas's describe of the materialized table, failing loudly. JSON rows carry `BIGINT` as strings (`COUNT(*)` reads `"240"`), so row-derived types misreport, and a fallback stores a guess as authoritative.
- **Spill-table schema inferred from the batch** → declined for a declared schema in `bls_get_series`. Inference types `value_numeric` `BIGINT` for whole-number batches and `VARCHAR` for all-unavailable ones, and the calculation strings `VARCHAR`, so the same SQL would bind against one batch and fail against the next.
- **Per-tenant quota accounting built into the server** → deferred. The 500/day limit is real but the server can't track cross-session usage without external state. Surfacing remaining quota from API responses (when available) is the right scope; full accounting is a deployment concern.

### Post-design corrections (verified against BLS API docs and LABSTAT)

- **`calculations` is a boolean, not an enum.** The initial design listed `calculations` as `enum: none, net_change, percent_change, all`. The actual BLS v2 API accepts `"calculations": true|false` only — an individual calculation type cannot be selected. The API returns whichever the survey supports (CPI/PPI return percent change only). The tool parameter is a `bool`, and per-survey support is indicated by `allowsNetChange`/`allowsPercentChange`.
- **No batch-latest endpoint exists.** The design's `timeseries/latest` POST endpoint does not exist in BLS v2. The actual endpoint is `GET /timeseries/data/{seriesID}?latest=true`, which accepts a single seriesID per request. `bls_get_latest` must issue N sequential (or parallel) GETs, each consuming one of the 500/day queries. Corrected tool description, quota note, and workflow analysis accordingly.
- **LABSTAT flat files are real and downloadable.** Confirmed at `download.bls.gov/pub/time.series/`. Each survey directory contains `{survey}.series` (the series index, sizes range from ~100KB to 15MB) and code-mapping files. The `{survey}.data.*` observation files (hundreds of MB each) are NOT needed for catalog search and are excluded from the startup harvest. The index of the 22 default surveys holds ~267K series in ~83MB.
- **BLS has no API catalog search.** FAQ explicitly confirms: "We do not currently have a catalogue of series IDs." The offline flat-file approach is the correct workaround (and the only one).
- **`bls_list_surveys` can use live API endpoints.** `GET /surveys` and `GET /surveys/{abbr}` return live survey metadata including calculation support flags. Moved `bls_list_surveys` to `BlsApiService` with aggressive caching (30-day process-local TTL). Does not consume meaningful quota.
- **Error contracts added.** Typed `errors` contract declared for: quota exhaustion, invalid SeriesID, locked database, no data for period, calculations not supported, catalog unavailable.
- **`format()` completeness callout added.** All three data-returning tools must render their full observation data in `format()`, not just summaries — Claude Desktop sees only `content[]`.
